# SAQTA: refactor report · 29 October 2026

Scope: existing `batyrkekw/SAQTA`, preserving Next.js, FastAPI, SQLAlchemy, PostgreSQL and the Vercel/Render configuration. No production database was reset, replaced or migrated during this local task. Source publication and a successful hosted rollout are separate outcomes.

## 1. Removed from the product interface

The marketing landing page, About/Docs pages, pricing and subscription panels, financial scenarios and duplicated dashboard/inventory/impact/settings navigation are no longer exposed. `/` redirects to SAVE; old informational/operational URLs redirect into the two current areas. Older service code and tests remain for compatibility; historical data and subscription records were not deleted. There is no automatic synthetic dashboard, claimed savings, seeded offer gallery or automatic conversion of forecast surplus into a listing.

## 2. Interface

Two main navigation links: SAQTA SAVE and SAQTA FORECAST. Shared green/cream visual system, responsive cards and forms, accessible dialogs, mobile menu and persistent RU/KK/EN selection. The current frontend covers navigation, input labels, validation, server errors, statuses, empty states, chart legends and numerical/date formatting. User-entered names, descriptions and original file headers remain user content. Account changes remount private workspaces so a previous account’s in-memory results cannot appear after a new login.

The five-step questionnaire preserves drafts when switching language. A browser-specific issue in which the last Next button could become a submit button during a click was corrected: review and save are separate actions.

## 3. SAVE

A public API reads only real-origin, non-test offers. Search and filters include category, city, price, minimum discount and charity eligibility. Offers include quantity/unit, known original price, actual offered price, pickup address/window, expiry, seller description and optional database-backed photos. Unknown original prices are null rather than invented discounts.

New accounts start as consumers even when they request business/charity access. An operator grants verified roles with `app.roles_admin`; there is no public role escalation endpoint. Businesses publish explicitly confirmed physical stock and edit only their own listings. Consumers reserve/cancel and see order status; sellers confirm collection. Charity bulk requests contain quantity, beneficiary count and logistics, hold stock while pending and require seller approval. Negotiated terms are available only through organization requests. They are excluded from price/discount filters while their price is unknown; the seller must enter the agreed unit price when approving, so a negotiated offer is not misrepresented as free or a 100% discount.

Reservations reuse the existing transactional inventory service, with buyer-bound idempotency keys, conditional updates/locks, no overselling, cancellation/expiry release and status audit events. Photos are limited, decoded, checked and re-encoded to JPEG. Forecasts never manufacture inventory. Payment processing, transport dispatch and automated entity verification are not provided.

## 4. FORECAST

The two entry paths are file import and a questionnaire. Accounts store profiles, catalog data, daily actuals, import batches and forecast runs. Results include per-product/location status, actual history, future demand, known available stock, conditional production/surplus, data quality, model selection and explanations. Repeat requests with unchanged input reuse a persisted calculation. Viewing a page does not train or generate a forecast. Past forecasts can be compared with later recorded actuals.

## 5. Imports, questionnaire and XLSX

The importer accepts CSV and XLSX, supports multiple worksheets, UTF-8/BOM, UTF-16 BOM and Windows-1251, and recognizes RU/KK/EN header synonyms. Ambiguous matches require mapping. Dates, whole-unit quantities, missing values, impossible balances, duplicate/conflicting rows and formulas are checked before an all-or-nothing commit. Mapping changes invalidate the preview token. Duplicate reimports do not add sales twice. A new product needs a unit in the file or an explicitly entered default. Imported daily totals never create physical SAVE stock.

Batch metadata includes file hash, source label, selected sheet, options/mapping, quality warnings, missing values and row/duplicate counts. There is no silent overwrite of an existing different daily total.

The questionnaire stores business/workday information, products, optional typical quantities, shelf life and contextual factors as versioned JSON. Null is distinct from zero; assumptions never become historical observations. Estimates belong to one selected location and are not multiplied across branches. The exported workbook has `Business`, `Products`, `HistoricalData` and `Assumptions`, version/date metadata and literal text cells to prevent spreadsheet formula execution. `HistoricalData` contains recorded daily observations only, or headers when none exist. A workbook can be reimported for review without immediately writing its answers.

## 6. Numerical model

Baseline candidates: last observation, last-seven-observation mean, weekday seasonal value and the existing weighted baseline. With 98+ observed dates, a NumPy ridge regression using past-sales and weekday features joins the comparison. With 28+ dates, chronological model selection and a separate final seven-observation rolling evaluation produce actual MAE/RMSE/WAPE. Fewer than 28 dates do not receive invented quality metrics; fewer than three dates require history or explicitly provisional questionnaire estimates. Missing dates are not zeros and WAPE is null for an all-zero evaluation period.

This modest model runs on the existing Python server without a GPU or mandatory external AI bill. It is preferable to a large model without evidence of sufficient data. Numerical methods, evaluation semantics and licenses are detailed in [MODELS.md](MODELS.md).

## 7. Language model execution

An optional server-side adapter supports self-hosted Qwen3 with an OpenAI-compatible endpoint. The concrete Qwen3-0.6B weights and optional Transformers code have separately documented Apache 2.0 licenses. No weights or inference service were provisioned. No developer laptop or paid provider is required for core analysis.

The model is restricted to ordering known explanation fact IDs based on aggregate metrics. It cannot supply numerical forecasts, fabricate accuracy or invent new claims. Invalid output, timeout and unavailable inference keep deterministic explanations. The frontend requests this optional refinement only when the backend reports it configured.

## 8. Why real-data analysis previously failed

Several code-level gates combined: demo was the default mode; real-source uploads were correctly rejected by the demo provenance guard; real organizations then faced a manually activated subscription gate; and import required catalog products to exist before an unfamiliar product name could be resolved. There was no independent business-questionnaire path. The old interface mixed these requirements with demo, subscription and legacy analysis tools, making an unavailable analysis appear to be a file/model failure.

This diagnosis concerns the inspected repository and reproducible local requests. It is not an assertion that production logs or a hosted failure were inspected.

## 9. Fix

Default real mode, seeding disabled, isolated authenticated organizations, free current analysis/import, explicit optional catalog creation, worksheet/header mapping, reviewable errors and separate factual/estimated data. The source-origin safeguards remain: archived synthetic data is neither relabeled nor shown as real. Existing subscription records and the optional legacy subscription configuration remain compatible, while the current analysis workflow has no pricing gate.

## 10. Migration

`f5a6b7c8d9e0_real_workflows.py`, after `e4f5a6b7c8d9`, adds account roles, known-price metadata, listing terms/expiry/photos, buyer/bulk order fields, observation context/optional quantities, business profiles and order events. ## 12. Rollout requirements

Keep the existing Render service/database and Vercel project. Use the configured PostgreSQL `DATABASE_URL`; apply the migration through the existing container startup. Explicitly set `WORKSPACE_MODE=real`, `AUTO_SEED_DEMO=false`, `FORECAST_REQUIRES_SUBSCRIPTION=false`, and `CORS_ORIGINS` to the deployed frontend origin. Set Vercel’s `NEXT_PUBLIC_API_URL` to the existing HTTPS backend ending in `/api`, then rebuild. No model key is necessary for the core product.

Live Render settings were not inspected because no workspace was selected in the connected integration. Provisioning or changing a hosted environment was not performed. If Qwen refinement is desired, separately provision sufficient inference capacity and supply the backend-only endpoint/model/token variables. Verify the deployed build, migration and real account flows after rollout.

## 13. Remaining limitations

- A production rollout and operational inference hosting still require the existing environment configuration/access; neither is represented as completed.
- No online payment, automated business verification, delivery integration, email verification/reset or notification system. Roles are approved by an operator.
- Quantities use whole units; fractional weights must be expressed in grams. Monetary inputs are whole tenge. Mixed unit conversion is rejected rather than guessed.
- One profile’s provisional estimates apply to one location. The location count answer does not fabricate branch records. New branches can be managed through the existing authenticated locations API.
- Forecast uncertainty intervals and causal weather/promotion effects are not calculated. The holdout measures rolling one-step errors, not a guarantee of multi-day performance.
- Inventory does not have lot-level FIFO/expiry optimization; the seller must verify freshness. Forecast surplus is conditional, not an actual listing or a confirmed future balance.
- Conflicting daily totals require correction of the source and an explicit operator workflow; the importer does not silently overwrite stored facts. The XLSX history sheet exports the recorded daily-observation workflow, not an inferred complete day from individual SAVE transactions.
- Marketplace results and recent histories are bounded (200 offers/orders, 20 calculation runs displayed). The API retains historical records; large-scale pagination and background queues are future operational work.
